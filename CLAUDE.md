# Running Coach

This folder is David's running log; Claude acts as his running coach.

## Data
- Runs are recorded on COROS (upper-arm optical HR strap) and auto-sync to intervals.icu.
- `python scripts/sync.py [oldest-date]` pulls activities from the intervals.icu API
  (key in `.env`) into `data/activities.json` (raw) and `log.csv` (summary, miles / min per mi).
- Run the sync at the start of any coaching conversation to get the latest runs.
- `scripts/analyze.py` reads every FIT file in `data/fit/` (intervals.icu) and `data/coros_export/` (COROS bulk export zips, unzipped), de-duplicates by start time, and writes `data/laps.csv`, `data/runs.csv`, and `data/hr_hist.csv` (seconds at each bpm, drawn as the month view HR curve), `data/trace.csv` (HR, grade-adjusted pace via Minetti et al. 2002, and pace in 5 s bins, drawn in the week view), `data/efforts.csv` (fastest grade-adjusted 1 mi / 2 mi / 5K / 10K / half within each run, with clock time, net elevation and HR), `data/segments.csv` (steady laps, joined when consecutive laps share a pace: grade-adjusted speed and HR, for the HR-based fitness estimate), and `data/cross.csv` (hikes and XC skis: HR-zone load, never mileage). `laps.csv` carries grade-adjusted lap pace; `runs.csv` carries aerobic decoupling (Friel's Pa:HR, first vs. second half after the warm-up) and whole-run grade-adjusted time. Grade comes from USGS 3DEP map elevation along the GPS track (`scripts/elevation.py`, cached per run in `data/elev.csv` as elevation vs distance, no coordinates), falling back to the barometer plus rolling 7d/28d mileage. Some runs (e.g., 2026-09-20) never reached intervals.icu, so re-export from COROS if totals look low.
- `config.json` holds the athlete settings the scripts use: time zone, home (name, elevation), HR thresholds (AeT/LT/max, resting), altitude methods (Daniels s/mi per 1,000 ft above a floor; path to the NCAA table), load for manual runs, load ramp (acute:chronic windows and Gabbett's thresholds), decoupling (minimum minutes, 5% limit), best efforts (distances), HR-based fitness (lap settling time, minimum minutes, pace steadiness, rolling days, races to calibrate on), workouts (pace tolerance, minimum rep length, threshold HR band and 90th-percentile ceiling), and cross-training (which FIT sports count, plan keywords, default load per minute before any recorded sessions). When a threshold changes, edit config.json only; zones, labels, and method notes are derived from it.
- `races.csv` lists races (date, name, location, distance, elevation, course notes). The next upcoming row is the "next race" on both pages. Add new races here.
- Altitude conversions use two published methods, shown as a range (`scripts/config.py` `convert_time`): Daniels and the NCAA 2009 tables. Sources are in `data/ref/README.md`. Don't invent altitude factors.
- `profile.md`: narrative profile (goals, races, injury history). `notes.md`: subjective notes per run (`- YYYY-MM-DD: note`); a note saying "trail" keeps that run off the pace-at-AeT chart and out of the HR-based fitness estimate; "trail lap 2" (or "trail laps 2-3") leaves out only those laps, and the day view labels them. Marks made in the COROS app or intervals.icu don't reach the scripts, so trail runs go in notes.md.

## Context
- Lives in Flagstaff, AZ (~7,000 ft). Factor altitude into pace and HR interpretation.
- Uses imperial units.
- `data/prior_weeks.csv`: weekly totals David reported for Jun 15–Aug 17 2026, before the recorded data. They feed only the 12- and 26-week averages on the Mileage chart; a week that overlaps recorded runs adds just the remainder. He didn't run from Nov 2025 to Jun 14 2026, so the 26-week average starts with the 12-week line. His earlier running (Apr 2024–Oct 2025) is in `data/Running log - 2024-25.csv`, summarized in profile.md; it doesn't feed the site.
- Hand-made FIT files (e.g., when he forgets his watch) go in `data/manual_runs.txt`. They count toward mileage but are excluded from HR and pace analysis.
- `training-plan.md`: current block (Phoenix 5K, Dec 26 2026; switched from the 10K on 2026-10-15). Compare actual runs against it and adjust week by week.

## Publishing
- GitHub repo DaveEdge1/RunningCoach (public), with Pages served from `docs/`.
- `scripts/build_site.py` builds `docs/index.html` (calendar) and, via `scripts/fitness_page.py`, `docs/fitness.html` (Fitness tab: mileage, training load, pace at AeT, zones, load projection to race day with the acute:chronic load ramp, workouts vs. targets, fitness vs. goal, best efforts, VDOT) from `plan.csv` and `data/`.
- `scripts/calculator_page.py` builds `docs/calculator.html` (Calculator tab): race predictions with 80% ranges from any mix of recent races, LT2 pace, LT1 pace and weekly mileage, all optional (seeded from races, pace at AeT and the 28-day mileage). The center is VDOT shifted by how real runners miss it and the range is the 10th–90th percentile, both from `data/ref/race_errors.csv` (thepowerof10 club results, split by VDOT band; rebuild with `python scripts/race_errors.py`, needs openpyxl, which also checks it on held-out runners and the Vickers & Vertosick survey). The marathon uses Vickers & Vertosick's weekly-mileage models (FiveThirtyEight's calculator) when mileage is entered. LT1 counts only when there's no race or LT2. The math runs in the browser; sources are in `data/ref/README.md`.
- Workout reps are matched to laps by effort, not distance: N comes from the plan session's "N × D" (e.g., "4 × 1 mi threshold" or "4 × 7 min threshold"), and the reps are the N laps of at least `rep_min_secs` with average HR ≥ AeT and the fastest grade-adjusted pace. Keep that wording in `plan.csv` and remind David to lap each rep. Threshold reps are judged on average HR in `threshold_hr` (160–167) and a per-lap 90th-percentile HR (`laps.csv` `hr_pctl`) at or below `hr_ceiling` (170); the first rep may sit low.
- Current fitness is the latest race or time trial only. Training best efforts never stand in (changed 2026-10-16: a fastest window can include recoveries, and training is submaximal by design); they stay as a record in the Best efforts table.
- Fitness vs. goal plots races plus an HR-based estimate per run: Daniels' VO2 cost of grade-adjusted pace over %HR reserve (Swain & Leutholtz 1997; resting/max HR in config.json), from steady laps, scaled to match the last races (Runalyze-style calibration), with a 28-day median (`rolling_days`; pace at AeT uses a 28-day median too). 14 days was tried on 2026-10-21 and was too noisy. Sources and the rejected %HRmax form are in `data/ref/README.md`. Lapping each rep keeps reps and jogs in separate laps.
- Cross-training: record hikes/backpacking and XC skis on COROS with the arm strap; they add load, not miles. Planned ones need minutes in `plan.csv`'s `cross_min` column and a keyword (hike, backpack, ski) in the session.
- A GitHub Action (`.github/workflows/update.yml`) does the same, started every 30 minutes from 7 to 11 am Arizona by a cron-job.org job calling the workflow_dispatch API (fine-grained token, Actions read/write on this repo only; set up 2026-10-23 because GitHub's own schedule dropped all but one run a day and started that one ~4 hours late; GitHub's schedule was removed). Commits only when something changed, using the `INTERVALS_API_KEY` / `INTERVALS_ATHLETE_ID` repo secrets. It downloads FIT files fresh and never commits them.
- `bash scripts/update.sh` does it locally (pulls first, since the Action also commits). Use it after a COROS re-export or a manual FIT file, since those exist only on this PC.
- `data/runs.csv` and `data/laps.csv` are the permanent record: `analyze.py` refreshes runs whose FIT it can see and keeps the other rows as they are.
- When the plan changes, update both `plan.csv` (which drives the calendar) and `training-plan.md`.
- Never commit `.env`, FIT files, `data/coros_export/`, or `data/activities.json` (they hold the API key and GPS tracks). `.gitignore` covers them.
- Races and time trials for VDOT: any `races.csv` date or `plan.csv` row of type `race`, or a plan session that contains "time trial", on a day with a recorded run. Elevation comes from the run's FIT file (falling back to races.csv, then home). The result is the fastest window at the race distance (races.csv, or the distance in the session, e.g. "5K time trial"), so a warm-up and cool-down recorded in the same activity don't count; a run within `race_whole_run_tolerance_pct` of the distance is scored whole, and shorter runs that day (a separate warm-up) are ignored. Keep the distance in time-trial session names.
